# Threat Model (STRIDE) — living document

Scope today: the implemented foundation (patient slice, IPC, SQLite). Re-review at every phase gate.

## Assets

Patient identity + clinical data (highest sensitivity) · practitioner credentials (future) · encryption keys (future) · audit log integrity · backups · application/update integrity · dependency chain.

## Threat actors

Casual local user · malicious local user / insider with device access · malware on workstation · thief with the device · malicious imported file (future) · compromised dependency · compromised update channel (future) · malicious AI content (future) · practitioner error.

| T-27 | Clinical identity data silently rewritten or hidden (T,R) | `patients` table | L | M | Demographic corrections go through `patient.update`: Zod `.strict()` schema, the file number is not editable (it identifies the record on documents already handed out), and the write is guarded by optimistic concurrency — a stale update fails with CONFLICT instead of overwriting. Archiving (`patient.set-status`) is reversible, deletes nothing, and leaves every consultation, measurement and document in place; archived patients still travel in backups and exports. Both actions are audited with the file number and version only — never names or contact data. | Implemented + tested |
| T-28 | A wrong household measure silently multiplies a prescribed amount (D) | `food_servings` | M | M | Grams stay authoritative: every total, the shopping list and every calculation use them, and the printed amount always shows them. When an amount is entered in a measure, the RENDERER names the measure and the main process looks it up and computes the grams itself, so a stale or hostile client cannot store a label that disagrees with the amount. The label is frozen onto the plan item (a snapshot, not a foreign key), so renaming or deleting a measure never rewrites a plan already handed to a patient; substitutions drop it, since the measure of the original food would misdescribe the replacement. The gram equivalent is shown in the picker and next to the input, so the amount is never ambiguous; a measure that no longer exists resolves to null and blocks the submit rather than falling back to grams. Measures can be deleted (a typo is not permanent) and deleting one leaves already-planned grams untouched. | Implemented + tested |
| T-29 | Archiving used as a back door to delete catalogue or clinical references (T,R) | `foods`, `recipes` | L | M | Archiving flips a status and nothing else: the row, its nutrients, its allergen tags and every plan item or recipe ingredient pointing at it are untouched, and plan hydration resolves by id without a status filter, so a plan already handed to a patient reads exactly the same afterwards. Only pickers and searches hide it, and `includeArchived` brings it back into view. Both directions are reversible and audited (`food.archive`/`food.restore`, `recipe.archive`/`recipe.restore`) with the name only — no clinical content. Bundled catalogue rows may be archived too (hiding the thousands of entries a practice never uses); reseeding is keyed on the source id and never resurrects them. | Implemented + tested |
| T-30 | Patient identity leaks through an OS notification (I) | Desktop reminders | M | M | A system notification is displayed outside the application: it can appear over a locked screen, be mirrored to a paired phone and is kept in the OS notification history — none of which this app controls. The body therefore carries the appointment TIME and nothing else: never the patient's name, file number or the reason for the visit (asserted by test). Reminders fire only while the app is unlocked, so a locked machine is never woken to announce clinical activity, and the practitioner can switch them off in Ajustes. Electron's renderer notification permission stays denied; the notification is created in the MAIN process. | Implemented + tested |
| T-31 | Patient-facing exports carry more than intended (I) | Progress report PDF, plan-as-text | M | M | Both are built from data the practitioner is already handing over. The progress report contains measured values and their trend only — no SOAP notes, no diagnosis, no interpretation — and every figure comes from a stored measurement, so it can never be rewritten by a later formula change. The plain-text plan carries no patient name: the conversation it is pasted into already identifies them, and a name in the clipboard is one more copy to lose. Both are written where the practitioner chooses, unencrypted by nature (like a printout) and audited with counts only. | Implemented + tested |
| T-32 | A lapsed subscription is used to withhold clinical records (R,D) | Licence write-gate | M | **H** | Records are clinical documents she is legally required to keep and patients have a right to; a billing dispute must never touch them. The gate refuses `write` channels only. Unlocking, reading, searching, exporting, printing, backing up and restoring are classified `always`/`read` and are never gated — including the auto-lock timeout, which is a security control and not a paid feature. The classification is a `Record<IpcChannel, ChannelAccess>`, so adding a channel without classifying it fails `tsc` rather than silently defaulting; an unclassified channel would fall through as NOT gated, which is the deliberate direction to fail in. Refusals are audited as `denied` with `reason: 'license'` and the channel — never clinical content. | Implemented + tested (`license-gate.test.ts` pins unlock/backup/export/print as ungated) |
| T-33 | Forged or replayed licence grants free use (S,T) | `userData/license.json` | M | L | Tokens are Ed25519-signed by an issuer key that never ships; the app embeds only the public half and verifies offline, so there is no licence server to compromise or to go down. The signature covers the token's payload segment exactly as written, so a re-serialized or hand-edited payload fails even with fields unchanged. Expiry is judged against the furthest instant the app has ever observed (`lastSeenAt`, monotonic), so winding the machine clock back buys nothing. Offline desktop software cannot be protected from a patched binary and this does not try to be: the goal is honest friction, not DRM (subscription.md §2). | Implemented + tested |
| T-34 | The licence store becomes a lockout or a data channel (I,D) | `userData/license.json` | L | M | The file holds exactly four fields — token, trial start, last-seen instant, and a random per-install UUID — and nothing about the practice: no patient counts, no usage, no hardware fingerprint (asserted by test). The device id is `randomUUID()`, deliberately NOT derived from the machine: a fingerprint would break on a disk or motherboard swap and would be a privacy problem, whereas a random id only ever answers "is one licence running on twenty computers". It is stamped on first run even while the layer is inert, so no install is left without one, and it survives activation and renewal so an honest customer is never indistinguishable from a shared licence. The schema accepts a file written before device ids existed, because rejecting it would fall back to EMPTY and silently restart the practitioner's trial. It lives outside the encrypted DB on purpose, so status is readable before unlock and "read-only" is never a surprise found after typing a passphrase. Every failure mode degrades toward MORE access, not less: a corrupt file, an unreadable file, or a token that does not verify all fall back to the trial rules rather than to a lockout, and with no issuer key compiled in the whole layer is inert. S-1 makes no outbound request at all; the egress rows in §T-20/T-24 stay the only network paths. | Implemented + tested |

## Standing rules

1. No raw SQL across IPC, ever, and no file path the renderer chooses. One narrow exception, added 2026-07-27: the automatic-backup folder is echoed back to the renderer read-only so the practitioner can see where their copies land. It is only ever _set_ from a native dialog in main (T-25), so the direction that matters — renderer naming a write target — stays closed.
2. New IPC handler ⇒ new row in this table + schema + audit behavior before merge.
3. Real patient data prohibited until the packaged apps (S-113/S-114) have been validated on real Windows/macOS. Backups (S-109) shipped 2026-07-22; the remaining gate is packaged-app verification.
4. No compliance claims (see assumptions A-11) without qualified legal review.
5. A path that will be written to may only originate from a native dialog in the main process — never from an IPC command field.
6. Nothing reaches an AI provider except through the de-identified context builder + `assertDeidentified` guard. Adding a field to that payload requires re-reviewing T-20 first; free text must never be added without a new injection + re-identification review.
